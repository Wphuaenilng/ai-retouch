## 1. 项目概述

### 1.1 一句话定位

一个自部署的 AI 修图工作台：**工具箱式的单项修图能力 + 自然语言 Agent 对话修图 + 图层化画布编辑器**，底层通过聚合国内云端图像编辑大模型 API 实现，无需 GPU，小范围邀请制分享使用。

### 1.2 目标与边界

**要做的：**

- 覆盖主流修图场景：文生图、抠图、换背景、消除（去水印）、局部替换、扩图、超分、调色、老照片修复等。
- 两套入口共享同一套工具：手动点按的「工具箱」和 AI 自动编排的「对话式 Agent」。
- 一个有真实体验下限的画布编辑器：图层、撤销重做、前后对比、选区与遮罩。
- 邀请制登录 + 用量配额（不做付费体系）。
- 一个不落俗套的视觉方案（见 §6）。

**不做的（明确排除，避免范围蔓延）：**

- ❌ 不做本地模型部署（不买 GPU、不装 ComfyUI）。
- ❌ 不做付费/充值体系，不做公开注册。
- ❌ 不做移动端完整编辑器（手机端只保证工具箱与简单查看编辑可用）。
- ❌ 不做视频、3D、批量高并发生产管线（P2 再议批量）。

### 1.3 目标用户与场景

用户就是你自己和收到邀请的几个朋友，典型场景：

1. **朋友圈/公众号配图**：上传一张照片 → "把背景换成纯白" → 导出。
2. **老照片修复**：扫描件 → 消除折痕 + 补色 + 超分 → 对比查看。
3. **电商式处理**：商品图 → 抠图 + 换背景 + 加文字。
4. **聊天式多步修图**："先把这张图裁成正方形，再提亮一点，背景换成咖啡馆" → Agent 输出计划卡片 → 确认执行。
5. **随手创作**：文生图 → 四宫格选一张 → 进编辑器微调。

### 1.4 与参考项目的关系

参考项目 [yuyuanweb/ai-picture-editor](https://github.com/yuyuanweb/ai-picture-editor)（原 ai-retouch-agent）是一个**教学项目**：React 19 + Konva 前端，FastAPI + LangChain/LangGraph 后端，21 种编辑工具，ARQ 队列 + Redis Pub/Sub + SSE，PostgreSQL + MinIO，Docker 部署。

**直接借鉴的：**

- 「同一套工具注册表同时服务 UI 和 Agent」的核心设计 —— 这是让工具箱和对话式修图不分叉的关键。
- 多步计划的「服务端校验（工具存在性 / 参数合法性 / 依赖补全 / 环检测）+ 拓扑排序 + 人机协作（确认 / 单步重试 / 取消）」流程。
- 任务队列 + SSE 实时推送的异步架构与交互形态。
- 画布编辑器的交互清单：视口缩放平移、图层文档、撤销重做、前后对比滑杆、SAM 式点选与笔刷选区。

**必须改掉的（因为技术路线不同）：**

| 参考项目                                | 本项目                                         | 原因                                                       |
| --------------------------------------- | ---------------------------------------------- | ---------------------------------------------------------- |
| 本地模型：rembg / SAM / 本地 inpainting | 云端 API：抠图与编辑全部走云 API               | 我们不走 GPU 路线，服务器只有 CPU                          |
| FastAPI + LangChain/LangGraph           | Node 22 + TypeScript，轻量自研 Plan-Execute    | 全栈同语言、单服务部署；聚合 API 场景不需要 Python AI 生态 |
| ARQ + Redis Pub/Sub                     | pg-boss（Postgres 队列）+ 进程内事件总线       | 少维护一个 Redis；小规模单进程足够，接口预留拆分能力       |
| MinIO 对象存储                          | 本地磁盘（Docker volume）+ 可选 OSS 备份       | 小范围分享，图片量级小                                     |
| 教学项目的"全能"范围（21 个工具）       | 收敛为 13 个 AI 工具 + 3 个本地工具（见 §3.2） | 每个工具都要有明确的引擎、成本与验收标准                   |

## 2. 同类项目与产品调研（2026-09）

### 2.1 开源项目

| 项目                                                                | 形态                                    | 可借鉴 / 不适合点                                             |
| ------------------------------------------------------------------- | --------------------------------------- | ------------------------------------------------------------- |
| [ai-picture-editor](https://github.com/yuyuanweb/ai-picture-editor) | 全栈教学项目，本地模型                  | 见 §1.4，架构与交互借鉴，模型层替换                           |
| [IOPaint](https://github.com/Sanster/IOPaint)                       | 本地 inpainting / 消除工具              | 交互上「涂抹 → 消除」的笔刷体验值得抄；本地模型与我们路线不符 |
| [Qwen-Image 2.1](https://comfy.org/zh-CN/qwen-image-2.1)            | 开源统一生成/编辑模型（7B，支持透明图） | 作为未来"混合路线"的备选；当前不用                            |
| ComfyUI 工作流                                                      | 节点式图像管线                          | 算子灵活性天花板，但学习曲线上限高，不做进产品                |

### 2.2 商业产品体验对标（只学交互与功效，不学视觉）

- **即梦 / 美图设计室**：工具箱的控件排布、结果对比方式。
- **Photoroom / Pixelcut**：抠图 + 换背景的一步式闭环（上传即抠图，这是很好的默认行为）。
- **Google Nano Banana 系产品体验**：多轮对话式改图时"保留一致性的二次微调"说法值得抄进提示词模板。

### 2.3 结论：差异化

1. **对话 + 工具箱双入口共享同一套工具**（多数商业产品只有其中一种）。
2. **计划可见、可干预**：Agent 的多步计划以卡片形式让用户确认、单步重试，而不是黑盒一次出图。
3. **国产 API 组合直连**：不翻墙、不代充、单价 ~0.2-0.3 元/张，成本可控可算。
4. **视觉与体验有主张**（见 §6），不是又一个紫色渐变的 AI 套壳。

### 3.3 画布编辑器（桌面优先）

对标一个"能用的"而非"玩具级"的编辑器：

- **文档模型**：一个文档 = 画布尺寸 + 图层数组 + 历史栈 + 来源图。持久化为 JSONB，切换图片再切回来不丢（学参考项目）。
- **视口**：滚轮缩放（以光标为锚点）、空格拖拽平移、`Cmd/Ctrl+0` 适配、`1:1`。
- **图层**：缩略图列表、显隐、不透明度、混合模式（P1）、拖动排序、上移下移、复制、删除。
- **变换**：Konva Transformer 实现移动/缩放/旋转；裁剪用遮罩 + 裁剪框两种模式。
- **撤销/重做**：文档快照栈（结构共享），容量 50 步；AI 操作的结果也是一个可撤销的步骤（重要：让用户敢于尝试）。
- **前后对比滑杆**：按住拖拽对比原图与当前合成结果。
- **选区**：矩形/套索 → 生成 alpha mask（黑白图）→ 传给服务端 inpainting；笔刷大小可调，支持按 `[` `]` 快调。
- **导出**：合成所有可见图层，支持缩放倍数、格式与质量。

性能红线：图片以「编辑用副本（最长边 ≤2048）+ 原图」双份存储，编辑永远在副本上操作，导出时按需对原图应用操作参数。

### 3.4 Agent 对话修图

一次请求的完整链路（与参考项目一致，但校验与执行在 Node 侧实现）：

```
用户输入自然语言
  → 规划器（LLM，结构化输出 JSON 计划，步骤带依赖）
  → 服务端校验：工具存在性 → 参数 schema 校验 → 依赖补全 → 环检测 → 拓扑排序
  → 计划卡片呈现给用户（可确认 / 改参 / 删步 / 取消）
  → 用户确认后按序执行：
       前端工具 → 直接下发指令给画布执行
       服务端工具 → 提交任务队列 → SSE 推送进度
  → 每步完成即时反馈到画布，失败可单步重试
  → 全部完成 → 生成结果快照，进入可撤销历史
```

- **规划提示词**：把工具注册表的 JSON Schema 作为 function calling / 结构化输出约束喂给模型；要求输出 `{ steps: [{ id, tool, params, deps, reason }] }`。
- **多轮上下文**（P1）：将最近 N 步操作摘要 + 当前画布状态喂回，支持"再亮一点""刚才那个背景去掉"。
- **失败体验**：单步失败不影响已完成的步骤；给出人话错误（"消除失败：模型返回内容审核未通过"）而不是堆栈。

### 3.5 账号与配额（小范围分享的轻量实现）

- 邀请码注册（注册时校验一次性邀请码），用户名 + 密码（argon2 hash），JWT 放 httpOnly Cookie。
- 配额：默认每用户每天 **30 次 AI 调用**（前端/本地工具不计），管理员可在管理页改。
- 超限行为：友好提示 + 当日剩余量展示；不做充值。
- 内容安全：所有生成/编辑请求过一遍图片审核（见 §7.1），未通过的图不返回、不计费。

## 4. 技术架构

### 4.1 总体架构

```
┌───────────────────────────── 浏览器 ─────────────────────────────┐
│  React 19 + Vite + TypeScript 单页应用                           │
│  ├── 工具箱页（上传/工具表单/结果对比）                          │
│  ├── 编辑器页（Konva 画布 + 图层面板 + Agent 对话侧栏）          │
│  └── 状态：Zustand（编辑器文档/历史/选区） + TanStack Query（服务端态）│
└───────┬──────────────────────────────────┬───────────────────────┘
        │ REST (JSON)                      │ SSE (/api/events)
┌───────▼──────────────────────────────────▼───────────────────────┐
│  Node 22 + TypeScript 单体服务（Docker 一个容器）                │
│  ├── HTTP 层：Fastify/Hono（路由、鉴权、上传、校验)              │
│  ├── 领域服务：auth / documents / tasks / agent / quota          │
│  ├── Provider 抽象层：seedream │ wanx │ mock（可扩展）           │
│  ├── 任务队列：pg-boss（Postgres 持久化）→ 内置 worker           │
│  ├── 事件总线：进程内 EventEmitter → SSE（预留 LISTEN/NOTIFY）   │
│  └── 图像处理：sharp（缩略图/格式转换/本地合成导出）             │
└───────┬───────────────────────┬──────────────────────────────────┘
        │                       │
┌───────▼────────┐   ┌──────────▼───────────┐   ┌────────────────┐
│ PostgreSQL 16  │   │ 本地磁盘 /data/images│   │ 云端模型 API    │
│ 业务数据+队列  │   │ （Docker volume）    │   │ 火山方舟/百炼等 │
└────────────────┘   └──────────────────────┘   └────────────────┘
```

设计原则：**单进程单体优先**。你的规模（≤10 人）用不上微服务；但所有跨进程边界（队列、事件、存储、Provider）都按"以后可以拆"的接口写，拆的时候不改调用方。

### 4.2 前端架构

```
src/
├── app/                    # 路由、布局、全局 Provider
│   ├── routes/             # /login /studio(工具箱) /editor/:docId
│   └── providers/          # QueryClient、Auth、Toast
├── features/
│   ├── auth/               # 登录、邀请码注册
│   ├── studio/             # 工具箱：工具卡片、参数表单、结果九宫格/对比
│   ├── editor/             # 编辑器
│   │   ├── canvas/         # Konva Stage/Layer、视口、Transformer、选区
│   │   ├── layers/         # 图层面板、排序、透明度
│   │   ├── history/        # 撤销重做（快照栈）
│   │   └── compare/        # 前后对比滑杆
│   ├── agent/              # 对话面板、计划卡片、步骤状态
│   ├── tools/              # 前端工具实现（调色滤镜等）+ 工具元信息
│   └── tasks/              # 任务列表、SSE hook、进度条
├── shared/
│   ├── tool-registry/      # 与后端共享的工具定义（zod schema）
│   ├── api/                # axios/fetch 封装、SSE 客户端
│   └── ui/                 # 设计系统：tokens + 基础组件
└── styles/                 # tokens.css（颜色/字阶/间距/动效）
```

- **编辑器状态**：Zustand store 持文档（图层、视口、选区、历史栈）；所有变更走同一组 action，AI 指令与手动操作都调用这些 action —— 撤销、协作、重放全部自动成立。
- **服务端状态**：TanStack Query 管任务、文档列表、配额；SSE 事件推入 Query 缓存触发 UI 更新。
- **工具注册表（前端侧）**：每个工具一个 `defineTool({ name, title, icon, inputSchema, executor: 'client' | 'server', clientRun?, costHint })`。工具箱页面、Agent 计划卡片、参数表单都由注册表自动生成 —— 新增工具只写一处。
- **样式方案**：**不引入 Tailwind 默认皮肤**，用 CSS Modules + 一份手写 `tokens.css`（颜色/字阶/间距/圆角/动效时长集中定义），保证 §6 的视觉方向能落到统一变量上。可选 Tailwind v4 但必须清空默认 theme、只当工具类用。

### 4.3 后端架构


**任务生命周期**（`tasks` 表一行为一个任务）：

```
created → queued → running → succeeded
                     └────→ failed（可重试，最多 2 次，指数退避）
                     └────→ canceled（用户取消；能取消的只有排队中的）
```

- 每个任务记录 `provider / model / cost`，是配额统计与成本报表的数据源。
- worker 并发度全局配置（默认 3），防止对上游 API 打爆并发。
- 任务超时：默认 120s，超时置 failed 并释放并发槽。

**SSE 设计**：

- 端点 `GET /api/events`，按登录用户隔离频道。
- 事件类型：`task.queued / task.running / task.progress / task.succeeded / task.failed / plan.created / plan.updated / quota.changed`。
- 断线重连：客户端带 `Last-Event-ID`，服务端从内存环形缓冲（最近 200 条/用户）重放；兜底：重连后主动拉一次进行中任务列表。（**这一步不做直播就会丢结果，必须有**。）

### 4.4 Provider 抽象层（本项目的技术核心）

```ts
// providers/types.ts
export type Capability = 'text2image' | 'edit' | 'inpaint' | 'outpaint' | 'upscale' | 'segment' | 'portrait' | 'textRender';

export interface ImageTaskHandle {
  provider: string;
  providerTaskId?: string;
}

export interface ImageProvider {
  readonly id: string; // 'seedream' | 'wanx' | 'mock'
  readonly capabilities: Capability[];
  readonly pricing: Partial<Record<Capability, number>>; // 元/张，用于统计

  submit(req: ProviderRequest): Promise<ImageTaskHandle>; // 提交（可能同步返回结果）
  poll?(handle: ImageTaskHandle): Promise<ProviderResult>; // 只对异步型 provider 实现
}
```

- **路由**：`registry.pick(capability)` 按配置的优先级列表选 provider；某 provider 挂了或未配置 key 时自动降级到下一个。
- **参数归一化**：把统一的 `ProviderRequest`（图、mask、提示词、目标尺寸）翻译成各家 API 的字段差异（比如 mask 是 dataURL 还是文件、尺寸是枚举还是像素）—— 差异全部封死在适配器里，业务层只见统一模型。
- **Mock provider**：返回本地占位图（带参数文字水印），保证断网/无 key 时全链路（队列、SSE、画布、撤销）可开发可测试。
- **幂等与重试**：`tasks.id` 作为上游请求的幂等键；重试只发生在"确定未受理"或超时场景，避免重复计费。

### 4.5 Agent 设计

**不做黑盒 ReAct 循环**，用确定性的三段式（可解释、可测试、可回放）：

1. **Planner（LLM）**：输入 = 用户消息 + 工具 schema + 当前文档摘要（尺寸、图层数、是否有选区）。输出 = 计划 JSON。约束：最多 6 步；每步必须是注册表中的工具；参数只允许引用现有图层/选区 ID 或字面量。
2. **Validator（纯代码，无 AI）**：
   - 工具存在性校验（白名单）
   - 参数 zod schema 校验 + 类型/范围钳制
   - 依赖补全（"局部替换"依赖"选区"存在，等等）
   - 环检测（DFS），失败则打回重规划一次（附错误原因）
   - 拓扑排序产出执行序列
3. **Executor（代码）**：按序执行，前端工具通过 SSE 下发给当前画布执行并等待回执；服务端工具提交任务队列。每步结果写入 `plan_steps`，支持单步重试（重建该步及其下游）。

LLM 选型见 §5：规划是"结构化输出 + 少量推理"，用便宜的中档模型足够；提示词与 few-shot 全部版本化在 `server/src/services/agent/prompts/` 下，可回滚可比对。

### 4.6 数据模型（实际：node:sqlite，7 张表）

> 本节 2026-09-24 按 `apps/server/src/db/schema.sql` + `migrate.ts` 的真实 DDL 逐列重写。
> 原设计写的是 PostgreSQL + `plan_steps` 表 + JSONB，实际实现不是那样，差异都标在下面。

```
users         (id, username UNIQUE, password_hash, role[user|admin],
               quota_per_day, created_at,
               token_version INTEGER DEFAULT 0,   -- 迁移 #3：会话可按账号吊销
               consent_at TEXT NULL)              -- 迁移 #4：隐私告知确认时间
invites       (code PK, created_by, used_by, used_at, expires_at, created_at)
               -- expires_at 真的有值了（管理页造的码默认 30 天）
images        (id, user_id, kind[original|edit|result|thumb|mask], path,
               parent_task_id, parent_image_id,   -- 迁移 #5：同一次上传的派生关系
               width, height, bytes, mime, created_at)
documents     (id, user_id, title, source_image_id, canvas TEXT,
               thumb_image_id, created_at, updated_at)
tasks         (id, user_id, document_id, plan_id, step_idx, tool,
               status[queued|running|succeeded|failed|canceled], progress REAL,
               provider, model, input TEXT, output TEXT,
               image_id, mask_image_id, result_image_id,
               cost_yuan REAL, error TEXT, error_code TEXT,
               attempts INTEGER, charged INTEGER,  -- 0 未结算 / 1 已入账 / 2 已退还
               created_at, started_at, finished_at)
plans         (id, user_id, document_id, user_message, planner,
               status[proposed|approved|running|done|failed|canceled],
               summary, steps TEXT, cost_yuan REAL, created_at, updated_at,
               exec_token TEXT, exec_started_at TEXT)  -- 迁移 #2：执行抢占锁
usage_daily   (user_id, date, ai_calls, cost_yuan)  -- PRIMARY KEY(user_id, date)
```

与原设计不同的四处，以及为什么：

1. **没有 `plan_steps` 表**：步骤直接序列化在 `plans.steps` 这一列里，配合
   `exec_token` 做"同一时刻只有一个执行器能写"。多表结构在这种规模下只是让自己
   多写一遍 join。
2. **`canvas` / `input` / `output` / `steps` 是 TEXT 存 JSON，不是 JSONB**：
   SQLite 没有 JSONB；没有任何查询需要这些列的内部索引，需要过滤的字段都提到列上了
   （如 `tasks.status`、`images.parent_task_id`）。
3. **`cost_yuan` 是 REAL 不是 numeric(10,4)**：金额只在展示时 round，参与的是
   预算比较而不是会计结算，误差远小于上游报价本身的粒度。
4. **`kind` 用 `edit` 而不是 `edit_copy`**：DTO 与目录里都是这个词。

索引：`images(user_id, created_at desc)`、`documents(user_id, updated_at desc)`、
`tasks(user_id, created_at desc)`、`tasks(status, created_at)`、`plans(user_id, created_at desc)`。

约束与迁移：

- **没有外键约束**，但 `PRAGMA foreign_keys = ON` 是开着的 —— 也就是说"配了开关却
  没有可约束的声明"。归属与级联清理走应用层（`requireOwned` 与 §删除的 `purgeImages`），
  删除顺序在代码里显式控制，不依赖数据库级联。
- **迁移策略**：schema 版本记在 `PRAGMA user_version`，不是某张表。
  基线 `schema.sql` 只在 v0 新库跑一次；此后所有变更以 `MIGRATIONS` 数组**尾部追加**，
  每条迁移与它的版本号写在同一事务里，失败回滚并点名是哪条；库版本比代码新时拒绝启动。
  **给表加字段一律走迁移，改基线对老库静默失效**（这条以前踩过）。
- `journal_mode = WAL`、`busy_timeout = 5000`；退出时 `wal_checkpoint(TRUNCATE)` 收尾。
- 图片不进数据库，只存路径：`$DATA_DIR/images/<userId>/<imageId>.<ext>`。

- 单张图输入尺寸限制（最长边 ≤4096，编辑副本 ≤2048），失败/审核未通过不计费。
- 统计报表（`usage_daily`）随时看得到花在哪；每个任务都记 `cost_yuan`。
- 先烧免费额度：百炼 50 张 + 火山新用户额度，够把开发与内测期覆盖掉。

## 6. 视觉设计方向

### 6.1 设计原则

1. **明暗结构必须服务于修图这件事**：界面背景不能给图片"染色"，所以要么是严格中性的深灰，要么是明亮中性灰 —— 鲜艳大色块不进编辑器。
2. **图像的物理感**：修图是"处理一张具体的照片"，界面里要能感到"这张图是一个物"，有重量、有边缘、有对比基准。
3. **拒绝模板脸**（三条红线）：暖米底 + 高对比衬线 + 赭石点缀 ❌；近黑底 + 单一荧光色 ❌；报纸式细线密栏 ❌。
4. **多主题/多方向必须落在排版层面**（字族、方向、结构、材质），色相变化不算换方案。

### 6.2 视觉方向（**已拍板：方向 A 暗房**）

> **决策记录 · 2026-09-21**：选定 **方向 A「暗房」** 为正式视觉方向，界面设计图已按此出稿（`design/design-sheet.html`）。B / C 保留在下文作为对照存档；日后若要更换，成本集中在 `tokens.css` 与四个关键组件（顶栏 / 工具导轨 / 计划卡片 / 对比滑杆），界面骨架与交互不变。

**方向 A：暗房（Darkroom）— ✅ 已选定**

| 轴        | 设定                                                                                                                                           |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 明暗/材质 | 银盐灰阶：`#141416`（底）→ `#2A2B2E`（面板）→ `#E6E6E3`（文字），带极轻微噪点质感（模拟相纸银盐），**不是纯黑**                                |
| 字族      | 全界面无衬线 grotesk（IBM Plex Sans 类）+ **等宽字体（Plex Mono）承担所有数字**：尺寸、坐标、进度、参数值                                      |
| 排版/结构 | 工具面板像暗房"挂墙器材"：图标 + 短标签竖排成轨道；缩略图区是**接触印样（contact sheet）**网格（带齿孔边、帧号）；图像本身是画面里唯一高亮区域 |
| 强调色    | 暗房安全灯红（firebrick 调，只做状态色：进行中/激活），大面积仍是灰阶                                                                          |
| 关键动效  | 生成过程用"显影"：结果图层从灰到实、从低对比到全对比的 600ms 过渡                                                                              |

功能理由：深中性灰是专业修图软件的通用底色（不干扰色彩判断），安全灯红天然是"进行中"语义。风险：与"近黑底+荧光色"红线的距离要靠**银盐灰而非纯黑 + 红只做状态 + 印样结构**拉开。

**方向 B：标准光源台（Light Table）— 未采用（存档）**

亮底方案：中性冷白 `#F2F3F5` + 仪器灰；唯一功能色用印刷青（process cyan），黄色只做警告。字体偏"制图感"（窄体 grotesk + 等宽数字），控件做成"仪器面板"（旋钮式滑杆、刻度、读数区），图层视觉是"叠着的透明片"。适合喜欢亮色工作台的人；风险是亮色工具界面更常见，需要在"仪器感"细节上做到位。

**方向 C：选片桌（Contact Sheet）— 未采用（存档）**

冷灰纸面 `#E9E9E6`（**不是暖米**），强调色是编辑用的蜡笔橙红（高饱和、只用于圈注与选中），"上传→挑选→圈注→定稿"成为界面的叙事骨架：批次编号、打孔边、编辑批注条。手写体只出现在批注里。风险：纸感主题需要极好的纹理控制，否则会像"又一个复古纸"。

### 6.3 关键界面布局（方向 A · 暗房，桌面）

```
┌──────────────────────────────────────────────────────────────┐
│ 顶栏：文档名 · 撤销/重做 · 对比 · 导出            [用量/头像] │
├──────┬───────────────────────────────────────┬───────────────┤
│ 工具 │                                       │ Agent 对话    │
│ 导轨 │            画 布 区                   │ ├ 消息流      │
│ (图  │       （图像 + 变换框 + 选区）        │ ├ 计划卡片    │
│  标) │                                       │ └ 输入框      │
├──────┴───────────────────────────────────────┤               │
│ 胶片条：接触印样缩略图 / 历史结果              │ 图层 + 历史   │
└──────────────────────────────────────────────┘
```

移动端（360/390/430 与横屏）：编辑器只保留"查看 + 调色 + 导出 + 简单裁剪"；工具箱完整可用；所有工具条在窄屏**图标化**（保 44px 触控目标 + `aria-label`），不折行、不缩字号。

### 6.4 响应式与验收细节

- 断点：`<640`（单列、底部工具条）、`640-1024`（工具导轨收窄为图标）、`>1024`（三栏）。
- 触控目标 ≥44px；`env(safe-area-inset-*)`；iOS 输入框不触发缩放（font-size ≥16px）。
- 对比滑杆、进度条、计划卡片这三处是"每天都会看"的组件，要做细。

## 7. 非功能需求

### 7.1 安全与合规

- **内容安全**：所有上传与生成结果过阿里云内容安全图片审核（或模型自带审核），拒绝时返回 `MODERATION_REJECTED` 且不落盘、不计费。这是分享给朋友的产品底线。
- **隐私告知**：上传图片会传输至第三方模型服务（阿里云/火山），在首次使用与设置页明确告知。
- **鉴权**：JWT httpOnly Cookie + CSRF 防护；上传大小限制（单文件 ≤20MB）；速率限制（登录、上传、任务创建各自限流）。
- **密钥**：模型 API Key 只存服务端环境变量，前端永不接触。
- **备份**：Postgres 每日 `pg_dump`；图片目录每周增量到 OSS（ossutil/rclone）。保留 14 天。

### 7.2 性能预算

| 项                       | 目标                                                  |
| ------------------------ | ----------------------------------------------------- |
| 首屏（编辑器，含 Konva） | < 2.5s（4G 网络）                                     |
| 画布交互（拖拽/缩放）    | 60fps（图像用离屏缓存，缩略预览拖动，松手渲染全质量） |
| 上传 5MB 图              | < 3s（先本地压缩再传）                                |
| 单次 AI 编辑端到端       | 5-30s，期间必须有进度反馈；>10s 显示预估剩余          |
| SSE 重连                 | 3s 退避重连，重放最近事件不丢结果                     |

### 7.3 可用性与容错

- Provider 降级链：主 provider 失败 → 备用 provider → 明确失败提示（不静默）。
- 任务结果"三点落地"：DB 任务记录、磁盘文件、SSE 通知至少两处一致才算成功。
- 所有 AI 结果都是可撤销的一步，用户永远可以退回。
